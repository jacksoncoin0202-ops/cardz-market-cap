## 5. 經歷過啲咩 —— 六個真係食過嘅虧

> 每個都係「做咗一次錯嘢、查到根因、然後變咗 code」。呢節係最值錢嗰部分。

### 5.1 修正做咗但唔生效（input_sha 唔 hash code）
`[KNOWN]` stage 用 input hash 判斷「使唔使重跑」，但個 hash **只 hash 數據唔 hash code**。
於是改完 code 再跑，個 stage 見 input 冇變就 skip，**修正靜默唔落地**。
→ 修法：input_sha 加埋 code 本身。**形狀教訓：任何「skip if unchanged」都要問「unchanged 包唔包我啱先改嗰行」。**

### 5.2 有 gate 但零 call site
`[KNOWN]` 36h checkpoint SLA gate 一早寫好，但**冇人 call**（`rebuild_036.py:7636-7644` 個 comment 自己寫住 "gate existed but nothing called it"）。
→ 修法：喺第一次寫入之前 call。**形狀教訓：任何「有檢查但零 call site」= 冇檢查。**
→ ⚠️ 呢個形狀今日**仲有一個**：`validate_daily_release.py` 個 `self_test()`（§6.2 A3）。

### 5.3 lane 冇報錯但少收咗七成八
`[KNOWN]` 2026-08-11 09:30 嗰轉只打 **208/993**。
根因：`REFRESH_DUE_HOURS = 12` 一個常數同時答緊兩條問題 —— 「幾時**一定要**重收」（由 SLA 倒推）同「幾時**先至准**重收」。
前一晚 12:13 UTC 另一轉收咗 785 條，到朝早佢哋只有 10–12 個鐘大，全部判「夠新」跳過。
**個 lane 由頭到尾冇報過錯，張數就係靜靜少咗七成八。**
→ 修法：拆做兩個常數，PC lane `PC_REFRESH_DUE_HOURS = 0.0`。有 test 守住（`test_pc_lane_full_sweep.py`）。

### 5.4 daily.py 漏一個 flag 靜靜跌一半卡

**兩個反直覺結論（兩個都量過，唔准再試）：**

1. **加分頁會慢。** 4 分頁（46 分鐘）慢過 2 分頁（34 分鐘）—— 每食一次 429 就要全部分頁一齊停 30/60/120 秒，賺嘅蝕晒。
   樽頸係 **~0.5 goto/s per IP**，唔係分頁數。
2. **擋走圖／css 會反效果。** 一版產品頁向 `www.pricecharting.com` 打 **31 個 request**（15 圖 / 6 script / 4 css / 2 manifest / 2 xhr / 1 fetch / 1 document），
   睇落擋走 21 個就快三倍。實際 A/B（同設定、隔 3 分鐘背對背）：
   **唔擋 40/40 全清 2.05 s/頁；擋咗 38/40、兩次 429、3.69 s/頁。**
   Cloudflare 見到「瀏覽器」淨係攞 HTML 唔攞 css／圖，直接當你係 bot。**要扮足全套。**

→ 已落三道 test 閘（禁 `page.route` / `context.route` / `route.abort`，`PC_TABS <= 4`，`PC_SLEEP_SECONDS >= 3.0`），
   而且**即場證明過會 fire**（故意寫 `PC_TABS=8` + sleep 0.5 + 一行 `page.route` → 19/22 紅；還原 → 22/22）。

### 5.6 0.2% 失敗丟 100% 成果（今日最後修嗰個）

`[KNOWN]` 全量 993 張跑咗 **47 分鐘**，報告 `batch=993 ok=991 cf=0 fail=2 rateLimited=2`。
結果 `last_incr.json`：**`inserted 0, checkpointed 0`** —— 一筆都冇入庫。

根因兩層：
1. `refresh_pc_pages` 要 `ok == expected and fail == 0 and cf == 0` 先算成功 → **0.2% 失敗丟 100% 成果**。
2. 更深：worker 食到 429 之後付咗 30/60/120 秒共用 backoff，然後 `continue` 去**下一張卡** ——
   等咗嘅嗰張永遠唔會重試。**等完唔重試 = 白等**，而且個判決係終局。

而 429 實測率就係 0.2%，即係 993 張入面撞到一兩次**幾乎必然** →
**呢條 lane 喺無人睇住嘅情況下日日都會咁死。**

→ 修法（commit `8d223f83`）：擺返落隊尾重試（最疏嘅間隔），最多 `len(BACKOFF_LADDER)` = 3 次，
   撤返啱先加落 `out` / `results` 嗰個判死。
   `run_fetch_pool` 拆做兩層：有 Playwright 嗰層測唔到，queue/backoff/requeue 算術嗰層測得到。
   新 test 9 條，**實證會 fire**（`requeued = False` → 2/9 紅）。

### 5.7 同一個修正跑一轉，即刻用同一形狀嘅另一個 bug 打返轉頭

| | |
|---|---|
| 429 | 3 次，**全部重試成功** → `rateLimited: 0` |

**requeue 修正本身證實有效**，但同一轉揭出兩件事：

**(a) 上游 5xx 一樣要重試。** 嗰 10 條 URL **40 分鐘之前先啱啱成功過**（HTML 檔 mtime 03:38–03:42 JST），

→ 修法：5xx 自己一個 status、會重試，但**唔用共用 backoff**（單版嘢壞 ≠ 成個 IP 俾人限速；
   10 版 × 3 次 × 30/60/120s 會白白蝕半個鐘）。

**(b) 我自己上一個 commit 嘅 off-by-one。** `cf_or_fail` 加嘅時候只加 `out["cf"]`，

→ 修法：counter 由 `FAILURE_COUNTERS` 一張表話事，**加同減行同一條路** ——
   呢個形狀之後唔會再出（tier 1，唔係靠 test 守）。

commit `f86bb050`，test 由 9 條加到 **16 條**，實證會 fire（注入返兩個舊 bug → 11/16 紅，
CF 嗰條直接報 `fail = -1`）。
