## 點量

### C1 白角 — 量圓角三角區，唔係量角落一小塊

真卡圓角半徑約闊度嘅 5.5%。如果圖係照住卡、按 bounding box 切而冇挖走圓角，**圓弧外面嗰塊三角區就係遺留嘅拍攝背景**，通常係白色。

量法：每角取 `r = round(闊 × 0.055)` 嘅正方形，用 `(r-1-x)² + (r-1-y)² > (r-1)²` 圈出圓弧外嘅三角區，統計「不透明（alpha ≥ 200）且三通道都 ≥ 235」嘅比例。**≥ 60% 就算白角**。同時放寬到 `≥ 200`（淺灰）再數一次，捉住淺灰背景嗰批。

- `nativeRounded` = 四角三角區不透明比例都 ≤ 40%，即係真嘅有挖圓角。98 張。
- 98 張有原生圓角嘅，淺色方角一張都冇（交叉驗證通過，detector 冇假陽性）。

### C3 歪斜 — 量 alpha 裡面嘅卡面墨水，唔係量 alpha 本身

畫布正規化器出嘅 alpha 係**軸對齊圓角矩形**，所以就算裡面張卡係歪嘅，alpha 幾何一樣係正方正正。所以歪斜要對住墨水量，唔係對住 alpha 量。

量法：先取 `alpha ≥ 200` 嘅區域（卡宣稱佔嘅範圍），再取當中 `rgb.min < 235` 嘅「墨水」像素。沿墨水 bbox 中間 80% 逐行／逐列搵第一個墨水位置，取「後 20% 中位數 − 前 20% 中位數」做斜率。**斜率 ≥ 2px 算歪斜**。

### C2 係咪嗰張卡 — 只可以人眼

程式判唔到。做法係將卡合成落深色面板（模擬網站底色，白角同白邊唔會溶入白色 chrome），加洋紅色細線標出畫布真實邊界，然後逐張對住 `canonical_name` + `collector_number` 睇。

## 量度時嘅前提（讀數字之前要知）

1. **`opus-image-fix` 同一時間持有資產目錄嘅 claim**（`FILE_CLAIMS.md`，2026-07-27 01:35 起：`data/public/market-assets/**` + `apps/web/public/market-assets/**` + `manifests/image-qc.json`，任務係 EB02-010 換圖 + 22 張補圖）。即係我量嘅時候圖檔隨時被換。上面所有數字係 2026-07-27 當刻嘅切片，唔係穩定狀態。EB02-010（v8）現時磁碟上嘅檔已經變成 429×600 RGBA，睇得出換圖 agent 已經動過手，但**換上去嘅仍然係卡包照，唔係卡面**。

2. **資料庫嘅 QC gate 係死嘅，權威係 manifest**。`market_image_qc` 456 行全部 `public_allowed = 0`，所以「`market_image_asset` 最新 QC-pass」用資料庫走係零行。實際權威係 `manifests/image-qc.json`（623 筆，全部 `publicAllowed = true`）。我嘅解析鏈用 manifest。

3. **看板範圍用凍結檔，因為 `apps/web/src/data/boards.json` 已被 `claude-boards` 刪除**。用 `board-universe.json`（265 張：ptcg100 100 + tcg300 265 + op100 40，有重疊）。

4. **opaque_id 漂移**：`cmc_*` = sha256(tcg, language, set_name, collector, name)，set 名一改就靜靜換 key，manifest 嘅 `publicId` 會過期。所以 join 除咗 `publicId == opaque_id`，仲加 `resolverEvidence.sourceContentSha256 ↔ market_image_asset.content_sha256`（內容定址，唔怕改名）。解析結果 243 / 22，同 board-gaps 之前獨立審計嘅「22 張冇圖」完全一致。

5. **副檔名講大話呢個陷阱今次冇中**。243 個檔全部用 Pillow 探過真格式，全部真係 WEBP，`extLies` 全 False。呢個前提要寫明，因為佢係一開始就假設會中嘅。

6. **斜率量法改過一次（原本錯）**。最初用 alpha mask 邊緣做斜率，全部卡都量到約 0，同用戶親眼見到嘅歪斜矛盾。原因兩重：(a) 歪咗嘅卡邊緣輪廓係 V 形，前後中位數相減會互相抵消；(b) 更關鍵係 alpha 本身就係軸對齊嘅，歪嘅係 alpha 裡面嘅像素。改成量墨水斜率之後，我肉眼判 BAD 嘅 6 張全部 ≥ 2.0，判 OK 嘅 6 張全部 ≤ 1.0，門檻就係咁定出嚟。

7. **白角 detector 亦改過一次**。原本每角取 inset 2 嘅 4×4 一小塊，喺 716px 闊嘅圖上等於 4 個像素，正好落喺反鋸齒邊上，量到 124 張。改成量整個圓角三角區之後係 109 張，並且用洋紅底放大圖逐角目視驗證過（見 `sheets/corners-verify.png`：v107 角落見洋紅 = 正確嘅原生透明圓角；v9 / v11 / v20 / v2 圓弧外面係實心白 = 遺留背景）。**`qc-results.csv` 用嘅係三角法（`whiteCornersTri`），唔係 4×4 法。**

8. **白邊（`borderWhiteFrac`）單獨出現唔算 fail**。呢個 detector 會喺三種情況響：真缺陷（切歪留白底）、卡本身印白框（例如 v1 085/SVP 梵谷聯名白框，36%）、畫作邊緣本身淺色（例如 v4 / v27 Munch《吶喊》聯名，46%）。所以只有**同時歪斜**先當 fail（8 張），單獨白邊嘅 17 張標 `suspect`，冇入重做隊列，要人眼再判。

9. **`sheets/fails-01.png` 磁碟上嗰個檔已經唔係我睇過嗰個**。白角 detector 重寫之後隊列由 148 張變 120 張，重生成 sheet 覆蓋咗原檔。我實際睇過嘅 24 張已經明文釘死喺 `image_qc_deliver.py` 嘅 `FAILS01_AS_REVIEWED`，冇用「重算頭 24 張」呢種方式冒充。`fails-02` / `fails-03` 係重生成之後才睇，同磁碟上嘅檔一致。

10. **C2 覆蓋範圍**：人眼睇咗 86 張 —— op100 全部有圖嘅 20 張（用戶親眼見過 OP 卡有問題，所以整組睇），加上程式 fail 名單頭 72 張（按最佳板位排序，即最貴／最搶眼嗰批）。已檢查名單見 `counts.json` 嘅 `sheetsReviewed`。剩 157 張標「未檢查」，**唔當 pass**。實際睇到嘅 C2 缺陷全部係「唔係卡面」類（卡包照、佔位圖、水印樣本），唔係「認錯卡」類 —— sheet 2 同 sheet 3 各 24 張卡面同卡名全部相符。
